## 3. NL2SQL 97.1%：不是能力退化，是评测集歧义

**失败用例 M10**：「每种媒体类型有多少首曲目？」

| | SQL 写法 | 结果 |
|---|---|---|
| gold | `JOIN`（内连接） | 1 行 |
| qwen3-max | `LEFT JOIN`（左连接） | 5 行 |

**根因是数据 + 措辞的联合歧义，不是模型错**：

- `agent.sqlite` 里 `Track` 表只有 **20 行，全部属于 MediaTypeId=1**
- `MediaType` 表有 5 种类型（另外 4 种在当前库里曲目数为 0）
- 问题问「**每种**媒体类型有多少首曲目」——字面上 `LEFT JOIN` 的答案（把 4 个 0 也列出）**更完整**；gold 的内连接实际上只回答了「有曲目的类型」

**关键判断**：完整版 Chinook 的数据集里 5 种类型都有曲目，两种写法结果完全相同。
这个歧义**只在 Track 被裁剪成 20 行之后才暴露**。

**处置建议（待确认，未擅自改动）**：

- 方案 A（推荐）：问题措辞精确化 →「**有曲目的**媒体类型各有多少首曲目？」，口径唯一为内连接
- 方案 B：gold 改为 `LEFT JOIN`，接受「0 也要列出」的口径
- 方案 C：补齐 Track 数据到完整 Chinook，歧义自然消失

> 未直接修改的原因：这个数字要对外报，改评测集口径属于需要知情的决策。

## 5. 多轮对话 50% → 100%：一处门控漏判

### 现象

首次重跑 `eval_multiturn.py`，`fixed`（带历史）仅 **4/8 = 50%**，未达赛题「连续 5 轮以上准确」。

### 根因：指代消解的门控漏判

`_needs_context` 只用三类词做预筛：代词（他/她/那/这/该）、句首承接词（那/还有/另外）、「呢」。

而 **「排在第一名的是谁？」一个代词都没有** → 不触发改写 → 语义校验判定「未指明按哪个指标」→ 发起澄清。
同类还有「最高的是哪个班？」。

### 连锁破坏（关键）

一轮失败会**污染后续轮次**：

1. T3「排在第一名的是谁？」被澄清打断，该轮助手消息里**没有「刘志菲」**
2. T4「那第二名呢？」正常
3. T5「这两个人相差多少分？」的改写只能从更早的 T1 取到「贾淑兰」
   → 改写结果 `贾淑兰和邵晓秀…`，而正确对象是 `刘志菲和邵晓秀`

**一处漏判，毁掉两轮。**

### 修法

新增 `_COMPARATIVE` 正则（`第N` / `前N` / 最高 / 最低 / 最大 / 最小 / 最多 / 最少 / 排名 / 排第 / 倒数）
纳入门控。

| 对话 | 修复前 | 修复后 |
|---|---|---|
| A · 跨轮指代链（5 轮） | 1/5 | **5/5** |
| B · 省略指代（3 轮） | 1/3 | **3/3** |
| **合计** | 2/8（25%）→ fixed 4/8（50%） | **8/8（100%）** |

修复后改写证据：

```
T3 排在第一名的是谁？       ⇐「综合素质测评成绩排在第一名的是谁？」
T5 这两个人相差多少分？     ⇐「刘志菲和邵晓秀的综合素质测评成绩相差多少分？」
B/T3 那个班有多少人？       ⇐「2990007 班有多少人？」
```

**安全性**：无历史时一律走快路径，**单轮零影响**；
「一共有多少人参评？」等自足短问句仍不触发改写（未误伤）。

## 6. RAG 链路效率基准（`bench_scale.py --rag`）

### 实测数据

| 语料页数 | 索引块数 | 建索引用时 | 构建吞吐 | 向量召回 | 词法召回 | search 合计 |
|---|---|---|---|---|---|---|
| 200 | 1 090 | 78.4 s | 13.9 块/秒 | 213 ms | 27 ms | 1 670 ms |
| 1 000 | 4 749 | 282.7 s | 16.8 块/秒 | 205 ms | 156 ms | 1 464 ms |
| 4 000 | 40 892 | 2 468.9 s | 16.6 块/秒 | 285 ms | 1 061 ms | 4 524 ms |

### 三条可下结论的规律

1. **向量召回几乎不随规模增长**（213 → 205 → 285 ms，语料涨 20 倍，延迟只涨 1.34 倍）
   —— 近似 O(log N)，说明 ANN 索引确实生效了，向量这一路**不是瓶颈**。
2. **词法召回线性增长**（27 → 156 → 1 061 ms；语料 20 倍 → 延迟 39 倍）
   —— 典型的 O(N) 全表扫描特征，这是**已知瓶颈**，与脚本里预设的对照实验一致。
3. **索引构建吞吐恒定在 ~16.6 块/秒**（13.9 / 16.8 / 16.6）
   —— 吞吐不随规模变化，说明瓶颈在**外部 embedding 接口**，不在本地计算。
   这一点对扩容规划有意义：要缩短建索引时间只能提高并发或换更快的 embedding，
   加机器没用。

### 新发现：真正的延迟大头是一处重复的 embedding 调用

`search 合计 4 524 ms`，而「向量 285 + 词法 1 061 = 1 346 ms」**只解释了 30%**。
差额在 `_rerank()`（`tools/rag_tool.py:523-524`）：

```python
qv = self.embeddings.embed_query(question)          # ← 与向量召回内部那次完全重复
dvs = self.embeddings.embed_documents([i["text"] for i in items])   # 候选集重算相似度
```

一次 `search()` 实际发生 **3 次 embedding API 往返**：

| 序 | 调用点 | 是否必要 |
|---|---|---|
| 1 | `similarity_search_with_relevance_scores()` 内部对 query 编码 | 必要 |
| 2 | `_rerank()` 再次对**同一个 query** 编码 | **完全冗余** |
| 3 | `_rerank()` 对候选集文本批量编码 | 必要（要统一相关度口径） |

而基准脚本单独计时只覆盖了第 1 次，所以三项数字对不上 —— 这是**测量口径的盲区**，
不是测量错误，但如果不点破，报告里的数字会被质疑。

**优化路径**：在 `search()` 开头对 query 编码一次，向量召回改用
`similarity_search_by_vector(qv)`，`_rerank()` 直接接收 `qv` —— 可省掉一次网络往返，
按当前量级约 **0.3~1 s/次检索**。

> **未擅自实施**：改动落在检索主链路，必须先重跑 `eval_rag.py` 确认检索结果
> 与优化前逐条等价，再上线。这一条属于「已定位、待验证」的优化项。
